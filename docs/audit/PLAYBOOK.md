# 全面 Audit 怎麼做（給下一個 Claude session）

第一次是 2026-10-06（`docs/audit/2026-10-06/`）。這份寫下那次怎麼做、哪些東西已經變成例行 QA（不用再做）、哪些每次都要人或 AI 重新看。
例行 QA（每次改完遊戲跑的）在 `docs/QA.md`；全面 Audit 是隔一段時間、或大改版之後才做的事，花的運算多很多。

## 什麼時候做

- 大改版之後（新的空間、新的長故事線、新的系統）、或發布了三四版之後。
- 使用者說「做一次全面 Audit」。
- **不要**在每次改版都做：能自動驗的已經在 `python3 tests/run_tests.py --qa` 裡。

## 先跑例行 QA，不要重做它已經做的事

Audit 開始前先跑 `--qa`。它已經自動檢查的事（`docs/QA.md` 的清單），Audit 不再用人力重做：每顆商店按鈕有沒有反應、
一整天用點的走得完、三種手機寬度有沒有東西跑出畫面、分頁用手指拿不拿得到、玩家存檔「繼續營業」、故事有沒有綁日期、
以及 `tests/qa_known_open.json` 裡已知未修的問題。**已知未修的問題不要再當新發現回報**，只看它們是不是還在。

## 規矩（2026-10-06 使用者原話，每一次都適用）

- 「第一階段只 Audit。不要看到問題就自行改遊戲。不要新增 canon。不要新增劇情。不要重新設計角色。不要因為你覺得某個做法比較好，就直接把它變成 PROJECT_MEMORY 的規則。」
- 「如果無法確認是我的要求，標成『需要使用者決定』，不要自行補完。」（使用者是現實中的人；Dylan 只指遊戲角色。）
- 「能用實際 UI 點擊驗證的，不要只用底層 function 證明。」呼叫遊戲內部只用來「觀察」或「快點到某個狀態」，要在條目裡寫明。
- 「也不要為了討好我而硬找問題。沒有問題就說沒有問題。但「測試通過」本身不是沒有問題的證據。」
- 主觀的設計偏好不是 bug，標 [DESIGN]，集中到最後一次問。

## 工具

- **`tests/player.py`**：像玩家一樣操作（真的觸控或滑鼠點在畫面上的位置；滑鼠不能橫捲沒有捲軸的列；按鈕中心被蓋住就算點不到；
  故事面板開著、一句句點完；`restock()`／`start_day()`／`play_evening()`；`capture_on()` 記下所有跳出來的東西；`reload()` 模擬離開 App 再回來；
  `resize()`；`overflow()`；`strip()`）。在 `tests/` 底下的腳本 `from player import Player`。
- **`tools/qa/new_game_timeline.py`**：新玩家從第一天開始，各條故事第一次出現在第幾天（劇情節奏）。
- **`tools/qa/evening_census.py`**：一晚跳出多少則、哪一類、誰在說、哪句最重複（劇情 Audit 的數字）。
- **`tools/qa/life_visibility.py`**：存在但在別的分頁的生活，各佔營業時間多少、正常玩家大概幾晚撞見一次。
- 以前的模擬工具：`tools/sims/`（`story_per_day.py`、`staff_room_day.py`、`line_census.py`、`live_check.py`……）。
- **自動玩家的盲點**：測試的快速機器人 `__bot` 一到收店就直接跳到結算，**收店那段（Jill 回房間、Dylan 在書桌、收店時才觸發的故事）完全不會跑**。
  要看收店，用 `Player.play_evening()`（真的一幀一幀跑），或在收店時改用 `__evening(秒數)`（`tools/qa/new_game_timeline.py` 的做法）。

## 分組（2026-10-06 用了九組，同時跑）

每組一個背景代理人，各自寫自己的資料夾；**代理人不能寫報告檔**（harness 擋住），它們把發現用文字交回，主 session 再存檔
（`docs/audit/<日期>/wsN_*.md`）。每組給同一份共同說明（規矩、工具、存檔、發現的格式），再加上自己的題目：

| 組 | 題目 | 要交的東西 |
|---|---|---|
| A 新玩家 | 新遊戲 Day 1–5，用手指學會做菜、讀每一句教學與故事；第一個十分鐘的感受；375／430 抽查；使用者真的 Day 2 存檔 | 一分鐘一分鐘的敘述 + 發現 |
| B 中期 | Day 46–74 存檔從標題讀進來（舊檔轉換）；玩兩晚、每個房間分頁；**每顆按鈕實按**（商店、開店前、員工、日誌、設定，第二層也按）；選單畫面 375／390／430 | 按鈕表、截圖索引 |
| C/D 後期與回來的人 | Day 89／92 存檔：隔幾天回來看得出發生什麼嗎；玩兩晚、每個房間；玩家自己動手的一晚；營業中離開 App 再回來；揭曉後稱呼是否一致 | 發現 |
| 劇情 | 新遊戲前五天、成熟存檔一週、揭曉前後各兩天的每一句（`evening_census.py`）；按順序讀：沒頭沒尾、總結式、重複、搶話、前後矛盾、像不像台灣人說話、每一幕有沒有起承轉合；**最差的句子照抄、不改寫** | 逐字稿、最差 10 句、數字 |
| 手冊 | 每一節每一項分 A 需要／B 太細／C 開發背景／D 過時（附證明）／E 缺少；拿具體說法對照遊戲；提出給玩家看的結構（不改寫） | 分類表、結構建議 |
| 玩法深度 | 每道菜的輸入步驟分類（幾道菜幾種玩法）；Day 10／50／90 每個系統給玩家什麼決定；什麼都不做 vs 完美玩家的差別；錢在後期的意義 | 表格、診斷 |
| 看不到的功能 | 存在但在別的分頁或卡片後面的生活：在哪裡、多常、有沒有提示、正常玩家幾晚撞見一次（`life_visibility.py`） | 總表 |
| canon 來源 | PROJECT_MEMORY 等文件每一條規則：A 使用者明確要求（原話與檔案）／B 從實作來／C Claude 延伸／D 找不到來源；特別看絕對字眼（一定、永遠、只有、揭曉前……） | 對照表、需要使用者決定的清單 |
| 測試 | 每個測試的方法（真的點／呼叫內部／機器人／golden／不變量／靜態）、會抓到什麼；盲點；過去的 bug 當時抓不抓得到；**把新的盲點寫成 `tests/qa_tests.py` 的測試**（而不是只寫在報告裡） | 分類表、新的 QA 測試 |

**發現的格式**（每一條）：ID、標記（[BUG] [UX] [WRITING] [GAMEPLAY] [CANON] [DOC] [TEST] [DESIGN]）、嚴重度
（Critical：存檔或進度不見、卡死；High：功能用不了或看不到、錢錯、故事壞掉或順序錯；Medium：容易誤會、看得出來的錯；Low：細節）、
在哪裡、怎麼重現（玩家的動作）、看到什麼／應該是什麼、證據（截圖、原文照抄）、確定程度（點擊重現／很可能／懷疑）、
使用者玩幾分鐘內會不會注意到、是不是設計選擇。

## 做完以後

1. 主 session 自己重現最重要的幾條（看截圖、讀程式）。
2. 報告寫在 `docs/audit/<日期>/README.md`：十件最重要的事、使用者一玩就會抱怨的、Bug、UX、劇情、手冊、後期、看不到的功能、
   可疑的 canon、測試盲點、接下來最值得做的事、最後一次列出「需要使用者決定」。白話繁體中文，先講「打開遊戲會看到什麼」。
3. **能自動驗的新發現，寫成 `tests/qa_tests.py` 的測試**：已經修好的是一般測試；還沒修的放進 `tests/qa_known_open.json`
   （修好時它會提醒拿掉，從此變成那個修正的回歸測試）。主觀的（台詞、故事、好不好玩、看不看得到）不要硬寫成測試。
4. 報告引用的截圖複製到 `docs/audit/<日期>/img/`（壓成 256 色）；其他截圖不進 repo。
