## Phase 1：分析（摘要）

### 各區塊現況

| 區塊 | 大小 | 耦合 | 評估 |
|---|---|---|---|
| game data / recipes（`DISHES`、`ING`、客人、裝潢、成就、事件、`MEMS`） | 17 KB | 低：以 id 查表 | 資料驅動，可以放心擴充 |
| state & save（`newState`、`load`、`save`） | 1.4 KB → 3 KB | 中：`S` 到處被改，共 26 個 `save()` 呼叫點 | 已整理，見 Phase 3 |
| restaurant / service（`update`、客人狀態機、訂單、步驟式烹飪） | 27 KB | 中高：會碰到員工、突發事件、貓咪（安撫客人）、UI 提示 | 行為由測試鎖住 |
| economy（進貨、結帳、小費、工資、緊急叫貨、商店） | 分散各處 | 中 | 測試驗證「結束金額 = 開始 + 營收 + 小費 + 獎勵 − 工資 − 食材」 |
| rendering / animation（`drawScene`、廚房、人物、料理圖） | 約 100 KB | 中：座標來自共用的版面常數，由 `applyDY` 調整 | 效能瓶頸在這裡 |
| audio | 7 KB | 低：自成一區，只有一個 `setInterval` | 沒問題 |
| cat rendering | 6.5 KB | 低 | 沒問題 |
| cat personality AI | 58 KB（最大） | 內部高：`catDecide` 權重表、佔位表 `OCC` / `SIDE` / `perchOcc`、`RACE_CD`、`BAO_LAST`，還會讀客人和 Jill | 未來最容易出 regression 的區域之一 |
| customer AI | 在 service 內 | 中 | 由完整流程與黃金基準測試保護 |
| crew | 5 KB | 中：影響烹飪、帶位、收桌 | 沒問題 |
| events / incidents | 5 KB | 中：直接改 `R` 和 `S` | 沒問題 |
| UI / input | 35 KB | 低到中：畫面用 `innerHTML` 重畫，按鈕走單一事件代理 | 沒有監聽器累積 |
| main loop | 0.8 KB | 只有一條 rAF | 沒問題 |

**重複程式碼**：沒有重複宣告，也沒有明顯的複製貼上函式。點擊判定大多和繪製共用同一份座標（`SPOT`、`kitchenItems()`、`kitchenRects()`），只有包包櫃的點擊範圍是寫死的。

**共用狀態**：以下變數各自被多個函式改寫。
- `IDLE`、`sub`：各 8 個函式。
- `phase`：7 個。
- `R`：6 個。
- `bg`：5 個。
- `mainScreen`：4 個。
- `paused`：3 個。
- `applyDY` 還會改動版面常數（`FB`、`LH`、`ROWS`、`PASS`、`SPOT`、跳台高度），並重建貓咪。

這是未來新增畫面時最容易出錯的地方。

**效能**（無 GPU 的 headless Chromium，390×795，實測）：

| 項目 | 每幀耗時 |
|---|---|
| 營業模擬 `update` | 約 0.003 ms |
| 貓咪 AI `updateCats` | 約 0.01 ms |
| DOM 刷新（每 0.12 秒一次） | 約 0.01 ms |
| `drawScene`，DPR 1 | 約 6.7 ms |
| `drawScene`，DPR 2.5 | 約 25 ms |

- `drawScene` 在手機上有 GPU，會快很多。
- 每幀約 2000 次 canvas 呼叫，其中 4 次全螢幕繪製：清除、背景快取、黃昏色調、暗角。
- 每幀不會建立新 canvas，背景有快取。
- 結論：**邏輯不是瓶頸，繪圖才是**，目前不需要處理。

**記憶體與計時器**：

| 項目 | 實測結果 |
|---|---|
| requestAnimationFrame | 同時最多 1 個 |
| setInterval | 1 個（音樂） |
| 事件監聽 | 15 處，全部在啟動時註冊，連玩十天沒有增加 |
| setTimeout | 都是一次性的 |
| 暫存陣列（愛心、飄字、粒子、客人） | 都會清理 |
| `R` | 每天重建 |
| 評論 | 上限 80 則 |

**貓咪 AI 擴充性**：
- 每幀每隻貓會掃其他貓和客人，大約 O(貓² + 貓×客人)。5 隻貓時可以忽略，就算 20 隻也很便宜。
- 真正的風險在結構，不在效能：`catDecide` 的權重鏈越來越長；每個佔位都必須在所有離開路徑釋放，否則會出現「幽靈佔位」，家具被佔著卻沒有貓在用。
- 已加上佔位不變條件的測試。

**存檔**：

| 問題 | 評估 |
|---|---|
| 容量 | 照片每種回憶最多 1 張、共 10 張、每張約 5 KB，評論上限 80 則，整份存檔約 4–100 KB，只佔 localStorage（約 5 MB）的 1–2%。**近期沒有容量風險。** |
| 存檔失敗 | 原本完全沉默，`save()` 回傳 false，但沒有人檢查。 |
| 讀不懂的存檔 | 原本會被下一次 `save()` 直接覆蓋：JSON 壞掉或 `v!==1` 會讓 `load()` 回傳 null，遊戲開新局後的第一次存檔就會蓋掉它。**這是最大的存檔風險。** |
| IndexedDB | 目前不需要。等照片數量不再固定（例如每天一張）或解析度提高時再做，見 C。 |
| migration | 原本新欄位靠「缺什麼從 `newState()` 補什麼」，這個機制可行；但沒有版本升級的位置，唯一的舊資料轉換也寫錯了（見下方「保留的既有行為」第 1 點）。 |

### 保留的既有行為（發現但刻意不改，因為玩家看得到）

1. **舊存檔的外場助手和吧台手沒有轉成員工**。`load()` 先用 `newState()` 補上 `crewMig:1`，才檢查 `if(!o.crewMig)`，所以這段轉換從來沒有執行過。修正只需要一行，但會改變這類舊存檔讀進來後的內容，所以留給你決定。目前行為已由測試鎖住，並在程式裡加上註解。
2. 不營業時，Jill 的 x 座標每幀都被固定在出餐口（y 不受影響）。
3. 衛生檢查員的評論沒有經過 80 則上限，每次檢查會多留 1 則，增加得非常慢。
4. 不營業時如果螢幕高度改變（例如旋轉手機），店面深度會重算，五隻貓也會回到初始位置。
5. **打包問題（這項已修正，不影響遊戲本身）**：以前給你的 `jills-kitchen-single-file.html` 是 Artifact 用的片段，少了 `<!doctype>`、`charset` 和手機 `viewport`。直接用手機打開可能出現亂碼，或變成桌機寬度。

### A. 現在沒問題，可以繼續新增
- 料理、食材、客人類型、熟客、裝潢、成就、事件、回憶照片。都是資料表，而且新料理會自動被「每道菜完美做一遍」的測試涵蓋。
- 主迴圈、計時器、事件監聽、暫存陣列。
- 音效與音樂。
- 存檔大小。

### B. 建議近期整理（本次已完成）
- 存檔安全：保留讀不懂的存檔、記錄存檔失敗、提供明確的 migration 流程。
- 移除確認沒用到的死碼。
- 單檔版改由建置腳本產生，並修正 charset 和 viewport。
- 寫下擴充守則與不變條件：`docs/ARCHITECTURE.md`。

### C. 遊戲規模更大後才需要

| 項目 | 什麼時候做 | 怎麼做 |
|---|---|---|
| 照片移到 IndexedDB 或獨立 key | 照片數量不再固定，或存檔超過約 1 MB | 以 migration 搬移，而且確認新位置寫入成功後才刪除舊的 base64 |
| 拆分 game.js | 單檔超過約 500 KB，或多人同時開發 | 先拆資料表（`DISHES` 等純資料），再拆音效，最後才考慮貓咪 AI；需要加入建置步驟 |
| 集中畫面切換（`setPhase` / `showX`） | 新增更多主畫面時 | 依第 2 節的不變條件設計 |
| 繪圖最佳化 | 真的在舊手機掉幀時 | 把黃昏色調和暗角烤進背景快取，或把 DPR 上限降到 2。**畫面會有細微差異，需要你確認** |
| 貓咪行為改成資料表 | 行為數量再增加一倍時 | 把 `catDecide` 的權重鏈改成資料表，並把佔位與釋放包成統一 API |
| 包包櫃點擊範圍改用共用常數 | 家具可以移動時 | 和其他點擊判定一樣共用座標 |

### D. 目前最可能讓遊戲壞掉的前三個技術風險
1. **存檔演進**：版本或格式一改，舊流程會讓整份進度連同照片被覆蓋；存檔失敗也沒有任何紀錄。這兩點已處理。
2. **存檔裡記錄的 id**：料理、貓咪、回憶、員工角色的 id 都寫在玩家存檔裡。新增沒問題，但**改名或刪除會讓舊存檔一打開就當掉**，例如 `DISH(id)` 找不到料理。
3. **共用狀態與貓咪佔位表**：`phase`、`R`、`IDLE`、`sub`、`paused` 分散在多個函式設定；`OCC`、`SIDE`、`perchOcc` 必須在每條路徑釋放。這些問題不會馬上報錯，而是表現成「畫面卡住」或「貓不再用某個家具」。

### E. 重構順序（依收益和風險排序）
1. 建立測試與黃金基準（完成）。
2. 單檔建置（完成）。
3. 移除死碼（完成）。
4. 存檔安全（完成）。
5. 補上不變條件測試與文件（完成）。
6. 以下之後再依 C 的條件進行：集中畫面切換、貓咪佔位 API、照片儲存、拆檔。

## Phase 3：實際修改

每一步都做了以下檢查，才進行下一步：
- 全部測試通過（多檔版）。
- 沒有新增 console error：每項測試都會攔截 console error 和頁面錯誤。
- 畫面、動畫、貓咪行為和基準完全一致：由 `golden_frames` 和 `golden_scenario` 檢查。
- 舊存檔可以讀取。

最後在多檔版和單檔版都再跑了一次全部測試。

| 步驟 | 內容 | 驗證 |
|---|---|---|
| 1. 單檔建置 | 新增 `tools/build_single.py`，由 `index.html` + `style.css` + `game.js` 產生單檔版 | 單檔版的 10 張截圖、373 個畫面雜湊，都和多檔版逐像素相同 |
| 2. 移除死碼 | 刪除以下沒有任何地方呼叫或讀取的程式碼：<br>• `STAFF`（早已被 `ROLES` / `crew` 取代）<br>• `dishTime`、`autoFocus`、`comboT`、`chipRect`、`drawChip`、`ST_SHORT`、`WALLS`<br>• 4 個沒用到的區域變數<br>• 1 個 `if(false)` 分支 | ESLint 0 個錯誤、靜態分析沒有剩下未使用的宣告、全部測試通過 |
| 3. 存檔安全 | 1. 讀不懂的存檔先複製到 `jills-kitchen-save-v1-unreadable`<br>2. `load()` 拆成 `fillDefaults` / `legacyCrew` / `MIGRATE`（附 `SAVE_V`）<br>3. 存檔失敗時在 console 警告一次<br>4. 存檔格式沒有任何改變 | 用新舊程式各跑三天，以及讀取兩份舊存檔，**寫出的存檔逐字元相同** |
| 4. 測試加強 | 畫面狀態和貓咪佔位的不變條件、真實觸控測試 | 在未修改的 v13 上一樣通過 |

### 刻意沒有做的事

| 項目 | 原因 |
|---|---|
| 拆分 `game.js` | 約 40 個共用變數和 268 個從主迴圈可達的函式緊密交織。拆開需要加上建置步驟，或把共用狀態改成顯式傳遞，風險高，現在的收益低。目前用區塊註解、文件和測試來維持可讀性。 |
| 用 Prettier 重新排版 | 會改到每一行，讓檔案大一倍，也讓這次和基準的差異無法比對。目前以 AI 協助修改為主，密集排版的讀取成本反而較低。 |
| 集中畫面切換 | 8 個寫入點行為細節多，改寫容易產生細微差異。改用不變條件測試保護。 |
| 繪圖效能最佳化 | 會造成可見的像素差異，而且目前不是瓶頸。 |
| 照片搬到 IndexedDB | 照片數量有上限，容量風險低。改成非同步讀寫會讓存讀檔流程複雜很多。 |
| 修正上面四個既有行為 | 玩家看得到差異，應該由你決定。 |
| 移除存檔裡的舊 `staff` 欄位 | 為了維持存檔格式和舊存檔相容。 |
