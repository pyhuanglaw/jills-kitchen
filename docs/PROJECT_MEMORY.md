# Jill's Kitchen — Project Memory（設計 canon）

新的 Claude / coding agent 開工前必讀。這份只記「不知道就很容易把遊戲改壞」的規則，以及每條規則的原因（WHY）。
它不是遊戲介紹，也不是企劃全文：細節以程式碼、`docs/v24/` 裡玩家的原話、各版報告為準。

- **永久 canon** 在這份文件。**暫時狀態**（branch、版本、待辦）在 `docs/CURRENT_STATE.md`。
- 程式結構與擴充守則：`docs/ARCHITECTURE.md`。發布流程（唯一權威）：`docs/RELEASE_CHECKLIST.md`。
- 玩家原話（逐字）：`docs/v24/*.txt`（檔名有日期時間）。原話與本文件衝突時，以「時間較新、玩家明確確認」的那一個為準；判斷不了就問。
- 「玩家」＝ 這個專案的使用者：現實中跟你對話、提出要求的人。使用者在 iPhone 上玩，也讓太太 Jill 玩。「Dylan」在這份文件裡只指
  遊戲角色（2026-10-06 使用者：「「使用者」就是現在跟你說話的現實中的我；「Dylan」只用來指 Jill’s Kitchen 裡的遊戲角色。不要寫
  「使用者就是 Dylan」或把兩者視為同一個稱呼。」）。

**誰可以改這份文件**：玩家說「這個是 hard canon，寫進 project memory」，或做出明確的產品決策（例如「員工變多以後，我就是希望
Jill 明顯多休息」）時，找到這裡對應的段落更新、附上日期和原話、commit。台詞好不好、某幕細節，這類東西已經在程式裡，不用寫進來。
值得寫進來的只有三種：不看歷史很容易猜錯的、曾經刻意從舊設計改掉的、玩家有非常明確產品意圖的。

## 0. 怎麼工作（每個 session 都適用）

**來源各代表什麼**（不要用其中一種投票）：
玩家目前確認的決策 = 產品意圖 ｜ 本文件 = 記錄下來的產品意圖 ｜ 程式 = 遊戲現在怎麼做 ｜ 測試 = 某個時間點寫下的預期 ｜
舊報告／舊文件 = 歷史證據 ｜ git history = 什麼時候、怎麼改的。
程式或測試和產品意圖衝突時，那可能是 regression 或過時的測試，產品意圖不會因此自動失效。

**CANON / DESIGN CONFLICT：停下來問。** 兩個以上的規則、文件、測試、實作或歷史決策互相矛盾，又無法用明確的時間順序判斷哪個是現行
canon 時，停掉與這個衝突直接相關的昂貴工作，用下面的格式問玩家。不要用 regression、simulation、換 seed、看測試怎麼寫、看程式
怎麼寫來替玩家決定，也不要自己折衷。與衝突無關、安全且已定義的工作可以繼續。

```
CONFLICT FOUND
A：[規則 / 實作 / 測試 A]
B：[規則 / 實作 / 測試 B]
目前 code：[一兩句]
需要確認：[A 還是 B？]
```

**運算是付費的。** 目標是用最少必要的運算得到足夠可信的工程證據。昂貴操作之前先問：它回答一個還不知道的工程問題嗎？結果會改變下一步
嗎？還是其實是要玩家決定的產品問題（那就直接問）？targeted evidence 是否已經夠了？
- Full regression 只留給：release gate、跨系統的高風險修改、migration／存檔相容、有理由懷疑大範圍 regression 的修改。
- 發布前的 gate 跑完之後，只改測試、不改遊戲檔的修正：重跑那幾個測試即可（2026-10-03 rc8 的做法），發布的頁面和測過的一模一樣。
- 長時間模擬要有明確假設。GOOD：「比較 rc7.7 與 current 相同三個 seed 的 oven/prep 工作量。」BAD：「再跑 200 天看看。」

**REPORT ≠ STOP。** 回報（附 390×844 截圖）之後繼續做已定義的工作。只有 canon 衝突、不可逆的存檔／資料風險、缺少重大產品決策，
才停下來等玩家。

**Commit ≠ Push ≠ Publish。** commit＝repo 裡的安全檢查點；push＝備份到 GitHub；publish＝更新玩家實際在玩的頁面。WIP 隨時
commit/push；publish 只依玩家的發布指示（見 §10）。

**I / T / O。** I＝已實作；T＝測試或腳本跑過（headless 截圖也只算 T）；O＝玩家自己在手機正常遊玩時看到。永遠分開報告，T 不能
寫成 O，不可以宣稱 iPhone 上沒問題。living-world 的功能，「程式存在」≠「玩家感知得到」。

**不要把猜測說成事實。** 先查清楚再說（玩家 2026-10-02 21:03–21:05 對此非常不滿）。

**只用繁體中文**：遊戲文字、文件、回覆。`python3 tools/hans_scan.py` 掃簡體字（干貝、沉、宿舍是正確的繁體）。

## 1. 產品核心

《Jill's Kitchen》不是單純的餐廳數值經營遊戲。

| | |
|---|---|
| Restaurant Management | skeleton（骨架） |
| Cats | life |
| Characters | memory |
| Spatial Growth | progression |
| Stories | time |
| Life Album | evidence |

真正的 fantasy：玩家不是想把餐廳效率最大化，而是想繼續看 Jill、五隻貓、員工和熟客慢慢生活下去。
判斷新功能的核心問題：**玩家會不會因為想知道接下來會發生什麼，而願意再玩一天？**（不是「功能多不多」）

「替現在補以前」：與其一直加新 feature，不如讓現在已經存在的空間、人物、物件、習慣有可信的過去。常問：為什麼這個東西在這裡？
誰以前用過？為什麼現在需要？這個習慣怎麼形成？今天看似普通的事，是從哪一次第一次開始變成日常？
要追求的體驗：「我記得這裡以前不是這樣。」

**故事的門，用故事的鑰匙開；空間與豪華升級的門，用錢開。**（使用者 2026-10-07，永久架構規則，最終 canon；與舊 spec、舊 commit、
舊測試、本文件或程式衝突時以這條為準）也可以說：「經營升級控制玩家能做什麼；人物關係與時間控制這個世界會發生什麼。」
- Major character／relationship／life story 的時機，由人物關係、實際來訪、前面的故事事實、必要的事件順序、合理的故事間隔、真正的
  物理／世界條件決定。Money／rating／restaurant level／Fine Dining／JILL 主要控制購買、設備、容量、菜單、營運能力、空間擴張、收益、
  視覺上的豪華、optional dream projects，以及真正屬於成熟餐廳經營的內容。
- **每次新增 gate 都要能回答：「如果拿掉這個條件，故事世界會哪裡不合理？」** 答案如果只是「怕太早」「想讓玩家晚一點看到」
  「這是 late game」「需要 progression」，不構成理由。
- 移除舊 gate 後，不得偷偷補上 Day 25、Day 40、12 次來訪、30 天、隱藏聲望、另一個餐廳等級、另一個昂貴工程之類沒有世界因果的
  替代 gate。
- 故事在前、錢在後：故事走到（Jill 決定、打電話問房東……）→ 工程出現 → 才輪到玩家決定要不要花錢。不要 money-first → story-permission。
- Major character／major story arc／人物關係，原則上**不得**以 Fine Dining、JILL、restaurant level、rating 或昂貴的 optional
  project 作 prerequisite，**除非有直接、可解釋的世界觀或物理因果**（例：沒有鋼琴就沒有予安來 Lounge 彈琴；樓梯在側廳，沒有側廳
  就上不了二樓；《你喜歡予安？》予安本人在場景裡）。
- 不要用新的 Day X、rating、level 或其他 arbitrary gate 取代被移除的 gate。玩家可以因為自己的花錢選擇晚買東西；遊戲不要另外擋。
- Fine Dining／JILL 繼續存在，是「經營成就／豪華成長」：可以控制菜色、設備、收益、容量、裝潢、豪華 optional projects。
- 昂貴的 dream works（酒窖、昂貴裝潢……）照樣很貴，讓後期有錢的玩家有地方花錢；但不得成為重要人物故事的門票。
- 使用者原話：「重要人物、人物關係、major story arc，不得因為玩家賺錢較慢，而被昂貴的 optional project、Fine Dining、JILL、
  restaurant level 或 rating 長期鎖住。」「只有存在直接世界觀／物理因果時，設備或空間才可以成為故事 prerequisite。」

## 2. Story scheduler（`storyTick`、`LANE_CAP`、`LANE_GAP`，`js/game.js`）

**「一天只能一個 major story」是舊規則，不是現行 canon。** 2026-10-02 15:39 玩家：「一天可以不只一個劇情不然太慢」（commit
485c87e，rc7）。現行（2026-10-03 確認仍在、仍有效）：

- 一天最多 **2 個 major**、**2 個長篇故事的步驟（v24 lane）**、**3 個 minor**；ambient 不限。
- 包場的 Lounge 晚上（品酒之夜、主廚之夜）不跟要在 Lounge 演的故事晚上（例如予安試彈）同一晚；排在之前、沒辦成而順延的包場，
  在排今晚的客人時就算今晚（2026-10-03，玩家 Day 87：試彈遇上主廚之夜，彈給空的 Lounge）。這是避開互斥的晚上，不是一天一個 major。
- 同一天同一 lane 的兩段要錯開一段營業時間（`LANE_GAP`：major 20%、v24 10%、minor 4%），不會同一分鐘一起跳出來；開店前算 0，
  打烊是自己的一個時刻。
- 同一條故事仍然一步一步照順序走（各幕自己的條件把它們分在不同天）。
- 當天的 planned visit 為它而來的那一幕、以及等最久的那一幕，各保留一個 slot（`v24Held`、`majorOwe`），只在所有空 slot 都被
  預訂時才讓其他幕等。**只屬於這一天的那一幕（floor 0）先**：保留的幕比剩下的 slot 多時，留給 floor 0 的那一幕，為某人來訪而
  保留的那一幕改天（2026-10-09）。試酒那晚（`ken_tasting` 開店時就佔一個 major）替《配菜的酒》（`pairing_start`，Ken 付帳時）
  保留第二個 slot：WHY——Release Gate 的故事檢查抓到，怡君的《三個選項》佔走了那一晚第二個 slot，配菜的酒那一幕隔天才演，
  Jill 說「今晚那幾支」時已經是隔天。仍然一天最多 2 個 major。
- 沒排到不是消失：記為 miss，權重上升，之後再排（`storyMiss`）。

WHY：舊版一天一個 major，實玩太慢。之後覺得某條線太慢，先檢查是不是這條線自己的前置條件（2026-10-03 晴×阿拓就是這樣：
排程器正常，慢的是這條線自己的等待天數），不要先懷疑或改 cap。

## 3. Jill 的工作量與休息

**產品意圖**（2026-10-03 玩家）：早期 Jill 很忙、很多事自己做；員工慢慢補齊之後，餐廳不再凡事需要她，她因此真的有餘裕坐下、
休息、回私人房間、看電子書、滑手機、陪貓。員工增加的回報不只是營收或速度，玩家要在世界裡看到 Jill 有空。大量站著不動的 idle
不等於達成這個設計。

現行規則（rc8）：
- **有廚師，菜就不用 Jill 做**，包括新菜的第一份（「不管是不是第一次做那道菜，有廚師她就不用做」）。仍保留：廚師等級決定能做的
  難度；招牌菜和招牌甜點要 LV5。
- 某個工作站今天沒有自己的廚師時，別站有空的廚師會過去接那一站的菜，一次一道、先顧自己那站（`chefCover`）。
- **廚師不分工**（2026-10-10，使用者在 iPhone 上玩私人測試版：「廚師就有空都要做吧 不要分工了」「裝盤怎麼可以當作技能」）：新廚房裡
  每位廚師有空就接任何一步（備料、熱區、烤、裝盤、做飲料），沒有要學的位置，**裝盤不是任何人的專長**；每人原本的主力位置（例：
  阿德師傅的熱區）只是稍微快、穩一點，不影響誰去做（`chefProf`、`chefCore`）。料理難度仍看等級（🔒；招牌要 LV5）——建議保留，使用者
  沒有反對。WHY：2026-10-07 的技能骨架（主力、第二項 LV2–3、第三項 LV4–5，程式裡一直標著「提案」）讓第 1 級的阿德師傅只會煮和
  做飲料、LV4 才會裝盤；第 2 天就能請廚師以後，裝盤還是全部落在 Jill 身上。**這一條取代使用者 2026-10-09 決策第 3 項**（「前期裝盤
  權限：選 A，維持專長成長」「不開放所有廚師自動裝盤」，`docs/v24/cooking_final_decisions_2026-10-09.txt`）：那時使用者還沒在 iPhone
  上玩到第 2 天以後；玩了以後親自改掉（「已經確認廚師就是會煮不會裝盤」「裝盤怎麼可以當作技能」，`docs/v24/iphone_reports_2026-10-10.txt`）。
- **裝盤先去盤架拿空盤**（2026-10-08 編舞「拿空盤 → 走到食物旁 → 盛盤 → 端到出菜口」；2026-10-10 使用者：「裝盤應該要走到盤子在的
  地方」）：盤架畫在水槽下方、檯面前半邊，從檯子前面拿（`wfRack`）。WHY：原本走到水槽後面靠牆的地方，「那裏又沒有盤子」。
- **今日任務**（2026-10-10 使用者：「按鈕擋住冷盤台、點不到 而且今日任務也沒有叉叉可按 不知道怎麼關」）：清單開在按鈕下面、有 ×，
  點 ×、清單、按鈕或畫面其他地方都會收起來；廚房裡如果「庫存／今日任務／💬」會壓到可以點的東西（矮的電腦視窗、橫拿手機），
  那幾顆移到房間分頁旁邊（`chipsWhere`）。
- Jill 在**開店時**（營業時間前 10%）和**快打烊時**（88% 起）都在主廳迎客、送客，只有中間會休息；88% 時還在休息就起身；打烊時
  一定起身收店（`JILL_HOST`、`startClosing`）。WHY：玩家「你就設定jill開店和關店都會在主廳歡迎和送客」；也讓樾樾在打烊後
  出來等她一起回房間（rc7.3）這件事繼續發生。
- 休息沒有固定長度：直到真的有她的工作（`jillWorkload()>0`）或玩家點桌子才起身。
- **在房間裡她自己找事做**（2026-10-03 玩家：「Jill有房間後多讓他在房間有事做吧 自動會做的 看閨蜜機電視（可移動的）打手遊 我老婆
  常常跟網友打pubg 或跟老公聊天 看老公在幹嘛 跟貓咪互動」）：營業中的休息和打烊後都一樣——看電子書、把可以推的電視推過來看
  （營業中也會自己起身去推）、跟網友連線打手遊（偶爾對麥克風說一句）、跟書桌前的先生聊兩句、走到他背後看他在忙什麼、他不在
  房間時傳訊息給他、叫貓過來（牠們不一定來）、摸身邊的貓。工作一來立刻起身：打手遊的話會跟網友說一句「我先下了」；推到一半的
  電視留在原地、關掉。房間裡的對話只是房間裡的泡泡，不進日誌。（rc8.2 時這裡另外寫了「不寫他的名字」，那是當時的做法、不是玩家的規則；2026-10-05 起他頭上有名牌。）台詞照 Jill × Dylan 的寫法
  （`docs/v23/qa4_2026-10-01_dylan_dialogue.txt`）。程式：`ROOM_LINES`、`roomActWeights`、`restUpStart`。
- **長期方向**（2026-10-03 玩家）：Jill 的私人房間不是多幾個動畫，而是讓她在不需要工作時能自主在房間生活——自己選擇並持續進行
  休息、看 ebook、滑手機、玩手機／線上遊戲、看電視、找 Dylan 聊天或看他在做什麼、和房間裡的貓互動。玩家不用下指令。活動不要機械
  式平均輪播：受當下的人、貓、時間、她最近做過什麼影響，也可以長時間只是休息。不做需求值、疲勞值、玩家控制的 UI——這是 living-life
  layer，不是新的管理系統。rc8.2 是第一組活動，之後的 polish 沿這個方向擴充，不是做完了。

`jill_rests_when_staff_cover_the_floor` 背後的 invariant 有產品意義：不要為了讓它過就降門檻，也不要單純調高坐下機率；要找工作量
／分工／打斷的根因（2026-10-03 的做法：逐格統計 Jill 在做什麼，比較 rc7.7 與 current 相同的 seed）。
沒有「sous-chef」這個職位；「後期廚房團隊承擔工作」目前是用各站廚師加上 `chefCover` 做到的。

## 9. 故事與寫作

- 故事不是 quest list。重要的 authored scene 可以暫停營業（時鐘、訂單、壓力），玩家點擊推進，結束後精確恢復。Ambient 時刻是
  即時的、可錯過的，不必每次停遊戲。
- 三層：Authored Beat → Callback／Consequence → Ambient Life。**先真的發生過一次，之後才有資格變成日常。**
- 不要讓角色精準解釋自己的情緒。避免 AI 式總結句：「這裡真的像家一樣。」「大家已經不只是同事了。」「原來幸福就是這麼簡單。」
  「我終於找到屬於自己的地方。」「謝謝 Jill 給我們一個家。」「一路走來真的不容易。」「這就是新的開始。」
- 情緒用 routine、shorthand、空間、物件擺放、熟了以後少說幾句就懂來呈現。角色可以不知道、猜錯、誤會、改變主意、話講一半、不回應。
  不要讓所有 NPC 都像全知的心理師。
- Jill × Dylan 的台詞守則：`docs/v23/qa4_2026-10-01_dylan_dialogue.txt`；一次性事件與習慣：`docs/v23/dialogue_audit_2026-10-01.md`。

## 10. 測試、存檔、發布

**測試證明正確，不證明品味。** 不要為了讓測試變綠而改 gameplay。失敗先分類：1. 真的 gameplay regression；2. 過時的測試；3. 既有
已知問題；4. 測試工具／模擬的限制。不要一看到 fail 就改 production code。
- simulation bot 不等於真人：例如 bot 不會擴建，新遊戲跑 200 天仍是 Level 1，不能因此判斷 story scheduler 壞了。
- 不要 seed-hunt 到出現漂亮的數字。比較根因時，用相同的 seed 做 A/B 是合理的。單一 seed 的機率性測試失敗時，先在改動前後各跑同一組
  seed 比分布，分布相同才算是落差，並在測試註解寫明數字。
- normal play 的觀察才是品味、節奏、可感知度的最終判斷。

**存檔**：新玩家＝Day 1。既有玩家照常接續 local save（存檔跟著網址走）。Day 74 之類的成熟存檔是 migration／regression 的 fixture
（`tests/saves/`），不是新玩家的預設內容。新系統不得：重置既有故事歷史、重播大量舊故事、刪員工、破壞 Life Album 或珍藏照片、
改變既有角色身分。舊存檔的補課不等於新遊戲的 canon 時間線（例：`linMig` 把 Madame Lin 線標成「更早以前」的歷史，不重播、不宣布）。
不要再用「文字框複製」做備份（曾讓 iPhone 當機）。

**店主手冊**（遊戲裡的「小小店主手冊」，`GUIDE`）：改到遊戲的基本架構——不只是劇情，例如員工、廚房、營業規則、空間、經濟——就要
同時檢查手冊有沒有過時，不必等到發布（2026-10-03 玩家：「以後如果有改遊戲基本架構內容 不只是劇情的部分 都要檢查店主手冊」）。
手冊每一項要短、好讀，一行一件事；遊戲畫面看得到的細節、故事會交代的背景不寫進手冊（2026-10-03：「每一項都一大坨 很難閱讀」）。
手冊只寫店裡已經有的空間（2026-10-03：「每個空間等他出現才出現在說明書吧」）：側廳、戶外區、Lounge、二樓、休息室、包廂還沒出現，

（`js/game.js`，緊接在 `GUIDE` 後面）決定今天顯示哪些。寫到新空間的句子，就在 `GUIDE_WHEN` 加一條；改了被管的那句話，規則裡的字也要
