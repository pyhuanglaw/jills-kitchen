## 1. P0：跨日之後畫面一直很暗

**找到的東西。** 在這裡的 Chromium 無法重現「隔天還是暗的」：每一天開店的前幾幀亮度都和第 1 天一樣（`daylight_returns_every_morning` 量的是畫布中段的平均亮度）。傍晚的暗是 `tintFor(duskF())` 依 `R.t/R.dur` 算出來的，`R` 每天在 `startService()` 重新建立，`duskF` 在 prep 是 .25、營業初期趨近 0，所以「晚上的暗被帶到隔天」在程式邏輯上沒有路徑。`globalAlpha`／合成模式／`save`/`restore` 深度也每天每秒都驗過（`world_stays_visible_across_days`）。

**最有可能的真正原因（手機特有）：** 地板與牆是畫在一張**離屏 canvas**（`bg`）上的快取，快取鍵 `bgKey` 只在等級／裝潢／尺寸／菜單改變時換。iOS Safari 在頁面退到背景、或記憶體吃緊時，會直接丟掉離屏 canvas 的像素（變成透明）。之後每一幀 `drawImage(bg)` 畫出來的是空的，畫面只剩深色底色與桌椅人物——看起來就像「整個變暗」，而且**隔天也一樣**，因為 `bgKey` 沒變、快取永遠不會重做。這和使用者描述的「某天晚上變暗 → 打烊 → 隔天還是暗」完全吻合，也解釋了為什麼桌上的東西還看得到。

**修法（不是把夜間 overlay 調淡）：**
- `bgCheck(now)`：每 2 秒探測一次快取上一個地板像素，透明就 `bg=null` 重畫（`makeBg` 只花幾十毫秒，一天最多幾次）。
- `visibilitychange` 回到前景、`pageshow`（從 bfcache 回來）：`bg=null`、`DCACHE.clear()`，所有快取重畫。
- `startService()`：`bg=null; lastEv=null`，每一天從乾淨的白天狀態開始。
- `drawScene()` 第一行把 `globalAlpha=1`、`globalCompositeOperation='source-over'`、`filter='none'` 明確歸零，任何上一幀漏出來的狀態都活不過一幀。
- 夜間本身：`tintFor` 夜色終點從 `#A89CA8` 提到 `#C2B4C0`，沙發暗角邊緣從 168 提到 196——打烊後在手機上仍看得清楚，白天／傍晚／夜晚的變化保留。

**測試** `daylight_returns_every_morning`：三天，每天開店前 45 幀的亮度與第 1 天差 < 6；傍晚要比白天暗但 > 55%；每天晚上模擬「切到別的 App、回來時離屏快取已被清空」；營業中把快取清掉後 3 秒內必須自己重畫回來。

## 2. P0：切出去再回來音樂消失

**原因（讀現在的程式）：** `audioInit()` 只處理 `state==='suspended'`。iOS 在來電、Siri、切到別的 App 時把 AudioContext 標成 **`interrupted`**（不是 `suspended`），回來時不會自動 `running`；而且原本沒有任何 `visibilitychange`／`pageshow`／`focus` 的恢復處理，也沒有「下一次點擊時恢復」。BGM 的排程 `musicTick` 還在跑，只是 context 沒有聲音。

**修法：** `audioResume()`（不是 running 也不是 closed 就 `resume()`，promise 失敗吞掉）；`AU.ctx.onstatechange`（頁面可見時 300 ms 後再試）；`visibilitychange` 回前景、`pageshow`、`focus` 都呼叫；再加一個 capture 階段的 `pointerdown`/`touchend` 監聽：iOS 只允許在使用者手勢裡恢復，所以**回來後的第一次點任何東西**就會恢復。AudioContext 仍然只有一個（`audioInit` 有 context 就只 resume），不會重複建立、不會出現兩份 BGM。

**限制（誠實）：** 這個環境沒有 iOS 裝置，無法實測「切出去再回來」。程式路徑在 Chromium 驗過（suspend → resume），在手機上要靠 playtest 確認。

## 3. P0：存檔到底是什麼

**原本的架構：** 一份 localStorage（`jills-kitchen-save-v1`），`save()` 在打烊、購買、換日時寫。營業中沒有存檔；暫停選單裡沒有存檔；「設定」裡的手動存檔在營業中會回到**今天開店前**（因為 `R` 不存），玩家按了會以為存了「現在」。

**現在：**
- **A. 本機自動存檔**：一樣，加上營業中每 20 秒、按暫停、切到別的 App（`visibilitychange`）時的 **checkpoint**（下一項）。
- **B. 營業中「儲存目前進度」**：暫停選單與設定都有 `saveCardHTML()`：「✓ 本機自動儲存 · 最後儲存：DAY X · 19:42」＋【儲存目前進度】。營業中按它存的是 checkpoint（含店內狀況），不是開店前。
- **C. 備份與移轉**：【備份到檔案】【從備份檔恢復】，另外多了【複製備份文字】【貼上備份文字恢復】（下一節）。

**Checkpoint 保存多少：** `snapshotService()` 把 `R` 整個平面化：每組客人（狀態、桌子、耐心、位置、心情、拍貓等）、每張訂單與每道菜的狀態、每個爐台的工作與步驟、Jill（位置、手上的菜、目前工作、佇列）、每位員工的任務與手上的菜、每張桌子（髒／盤子）、時鐘、combo、天氣、事件、任務進度、排程指標。物件之間的關聯都改成索引，經過一次 `JSON.stringify/parse` 證明是純資料。`restoreService()` 反過來重建，並驗證數量、索引、狀態名稱、座標都是有限值；驗證不過就走**安全備援**：從 checkpoint 的時鐘重新開店（今天的營收、客人數、任務進度保留，店裡的客人重新入座），並用 toast 告訴玩家「無法完整還原」。標題畫面在今天有 checkpoint 時顯示「繼續營業 · 19:42」與「不繼續，從開店前重來」。

不保存的：貓的即時狀態（`CATS` 從來不存，重開後重新開始生活）、Jill 的沙發休息（還原後她站在沙發前，該做什麼就去做）、正在拍照的客人的手機動作。

**測試** `service_checkpoint_resumes_the_day`：玩到 20 秒＋有客人在座 → 暫停 → 重新載入 → 「繼續營業」→ 時鐘、客人數、桌子狀態、訂單、爐台工作、Jill 的佇列都一致 → 玩完當天 → 沒有殘留 checkpoint；再故意寫壞一筆 → 備援路徑要在同一個時鐘重開、房間淨空、toast 有說。

## 4. P0：手機上的單一備份檔

`exportSave()` 產生一個 `JillsKitchen_Save_YYYY-MM-DD_HHMM_DayN.json`（外殼 `{app:'jills-kitchen',kind:'save',v,exported,save}`）。恢復：選檔 → `FileReader` → `parseSave()`（是不是我們的檔、版本不能比程式新、逐版 migration、`fillDefaults`、合理性）→ **顯示「讀取這個備份？DAY n · $m」等玩家確認** → 才覆蓋。壞檔、別的 JSON、比程式新的版本：一個 toast，`S` 一個位元都不動（`save_backup_and_restore` 用四種壞檔驗）。營業中也可以備份／恢復（暫停狀態下）。

**下載那一步到底有沒有成功：** 在這個環境只能驗到「`<a download>` 被點、瀏覽器產生了下載事件、檔名正確、檔案內容可以再讀回來」（Playwright 的 `expect_download`）。iPhone 上 Safari 會把它放進「下載」或跳出分享面板，**Claude 的 artifact 檢視器裡的 iframe 可能連下載事件都不會有**——這裡沒有 iOS 裝置，我不假裝驗過。所以加了保證可行的第二條路：【複製備份文字】把同一份 JSON 放進剪貼簿（`navigator.clipboard`，失敗時 `execCommand('copy')` 備援），【貼上備份文字恢復】貼回來走同一條 `parseSave` 管線。在任何能複製貼上的環境都能移轉。

## 5–6. P1：Jill 營業中會休息，而且是因為真的沒事

**為什麼以前從來不休息：** `jillUpd()` 只要 `!J.cur && !J.q.length` 就把她拉回 `PASS`（出菜口）站著（`J.idle>2.2` → 走回 PASS），沒有任何「去坐下」的分支；`J.sit` 只在打烊的 table 分支用過。她的「閒」也沒有被量測過。

## 13. P2：料理研發重做

**以前**：從 45 種食材裡挑 2–3 種、付 $150、剛好等於隱藏配方就成功，否則只有「接近了」／「怪怪的」。

**現在**（`LABI`、`labEval`）：每種食材的卡片上寫著**角色**（主體／配料／調味／醬汁／飲品基底／飲品配料／甜點基底／甜點配料）、**味道**（清爽・濃郁・香氣・口感各 0–3 個 ↑）、**成本階**（$／$$／$$$）；食材依角色分組排列。選好之後、付錢之前就看得到：每一對的**相性**（很好／可以／不合）、**整體味道**、**可能適合**哪個工作站與類別（從含這種食材的料理推算——像是食譜書的常識）。廚房裡的食材只顯示到目前等級 +1 的料理會用到的（第 1 級 20 種，不再一次 45 種）。

試做結果一定有四種之一：
- **大成功**：正好是某道還沒研發的菜 → 解鎖。
- **成功料理**：包含整道菜的食材、多了一種 → 解鎖，並告訴你哪一種其實用不到。
- **有潛力的試作品**：命中一道菜 ≥ 2 種食材，或雙食材菜的主角＋正確角色的配料 → 這道菜的**研究進度 +1**（●○○），並說出「像是一道主餐（爐台）的雛形。牛肉排、起司片是對的，還缺 1 種配料」；三次就**研究完成**、解鎖。試作證明過的組合會標成「相性：很好」。
- **普通試作品**：說出為什麼——「甜的跟鹹的混在一起」「飲料的材料跟料理的材料混在一起了」「缺少主體」「兩種主體打架：X 跟 Y 都想當主角」「味道太重：調味太多」，再給一句提示（哪一對相性很好、主角比較適合哪個工作站）。已經會做的菜會說「這就是 X 的做法」。

「還沒研發的料理」清單每道顯示研究進度、食材數、主角是哪一種（進度 2 以上再多說要配什麼角色），直接買食譜仍可。等級或工作站還不夠時研究成果先寄放（`S.rdDone`），擴建或買了設備一進商店就自動加入。

**相性的來源**：「很好」只來自已經在菜單上的料理和試做證明過的組合；沒試過的組合只依角色判斷「可以」／「不合」——所以推理有用、但不會一眼看穿。

**能不能在不看答案的情況下解？** 測試 `research_is_solvable_from_visible_info` 用一個只讀畫面資訊的推理玩家（主角、食材數、角色、相性、工作站提示、每次試做的回饋）跑完全部 18 道：每道 1–16 次、合計 79 次（$11,850，直接買全部食譜要 $42,000）。任意「合理」組合（一個主角＋同世界的配料）37% 會做出東西（大成功／成功／有潛力），其餘是有理由的普通試作品；完全隨機組合 12%。

**修了一個舊 bug**：研發出的菜若工作站還沒買（例如第 2 天研發出布丁，冷盤台第 4 天才有），客人照樣點、永遠做不出來、貓還會一直安撫他，**那天永遠打不了烊**。現在 `stationOk(d)`：沒有工作站的菜客人不會點，開店前的菜單會標「缺少冷盤台，客人不會點」，研發時也會說「要先買冷盤台才能上菜單」。

## 14–15. P2：商店與開店前

商店最上方：「目前現金 $X」＋「明日預估基本備料 約 $Y · 建議保留 約 $Z」（`restockEstimate()` 依今天的菜單、庫存與預估客人數；`keepAside()` = 估計 × 1.15 + 100）。任何購買後現金低於建議保留就 toast「⚠ 現金 $…，可能不足以完成明天的建議備料（約 $…）」，卡片也會轉成警告色。不會擋購買。開店前畫面多了【‹ 返回升級餐廳】（第 2 天起）：回到同一個商店（標題改成「DAY n · 開店前」，開放的分頁以前一晚計算，不會提早解鎖），底部按鈕變成【回到開店準備 ›】而不是再一次「準備 DAY n+1」。這中間沒有任何不可逆的事：日期在按【開始營業】之前不會前進。

## 16–17. P3：生活相簿

**原本**：`S.mem`，13 種畫面各一張、拍過就不再拍，畫面是「8/10」式的收集。

**現在**：`S.album`，累積式：每種畫面的**第一張是「珍藏」**（永遠不會被換掉，等於保留舊照片的成就感），之後同一種畫面**隔 3 天以上可以再出現**，每天最多 4 張（其中一般照片 2 張），一般照片最多 30 張、滿了最舊的一張出去。舊存檔的 `S.mem` 照片自動搬成珍藏（圖片不再重複存兩份）。新增五種畫面：偷閒（Jill 營業中坐下）、膝上的重量（貓跳上她的腿）、被拍了（客人拍貓）、摸一下（蹲下摸貓）、留下來的人（Dylan 在沙發上）。每張照片記日期與時間（營業中是店裡的時鐘，打烊後從 21:30 往後推）、標題與**一句依畫面寫的話**（「樾樾坐在 Jill 腳邊。」「柔柔從角落跳出來，寶寶嚇了一跳。」貓名用玩家改過的名字）。**沒有整理照片的操作。**

相簿頁是拍立得：白框、微微歪斜、日期時間、「標題」、那句話、珍藏的紅色小標。三天有員工的遊戲會留 3–6 張；存檔 16 張照片時 102 KB。

**測試** `album_notes_and_journal`：舊 `S.mem` 搬成珍藏且不重複存；同種畫面同天／2 天不拍、3 天可拍；45 張同種照片後一般照片剛好 30 張、最舊的先出去、珍藏一張都沒少；每天最多 4 張；三天實際遊玩留下的照片有標題、時間、JPEG；日誌總覽與相簿分頁顯示正確、沒有「COLLECTION」字樣。

## 18. P3：熟客留言
