## 補貨：沿用原本的邏輯

- 按鈕還是同一個 `restock`（先 `returnOffMenu()` 照進價退回下架的，再 `restockPlan()` 公平分配），沒有另寫補貨算法。測試在第 92 天存檔先用開關把一道
  有庫存的菜下架，再按上面的按鈕：結果每一道菜的份數都等於 `returnOffMenu()`＋`restockPlan()` 算出來的，下架那道歸零。
- 卡片上的「還要補 N 份，約 $X」和按鈕上的金額，是**按下去實際會買的**（同一個 `restockPlan()`，在下架的退掉之後的冰箱上算，畫面上不買不退：`restockPreview()`）。
  以前按鈕上的金額是「每道菜差多少」加起來，冰箱放不下時會比實際買的多（第 92 天：寫 227 份 $24,110，實際買 223 份 $23,678）。
- 「冰箱裝不下今天的預估需求（約 N 份，容量 M）…」那句小字，換成使用者指定的「預估需求 N 份｜冰箱容量 M 份」，數字是 `S.today.sugCapped`（建議量被壓之前的總需求）
  和 `fridgeCap()`。舊測試 `stock_suggestion_follows_each_dish_and_counts_the_demand_it_missed` 原本檢查「冰箱裝不下」這四個字；改成檢查新句子和當天的數字
  （句子是使用者決策五指定的，原檢查的「說了冰箱裝不下」這件事沒有放寬，反而多比了數字）。
- 結算那一行的數字：`R.st.fr`（開店時記下：當天的需求、冰箱容量、開店時放了幾份；只在建議量被冰箱壓低、而且不是 Jill 自動備料的前兩天）＋
  `st.unmet`（賣完以後還有桌子想點的份數，本來就有，結算每道菜的「估計少賣」用的同一個）。
