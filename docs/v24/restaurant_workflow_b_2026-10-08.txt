我要新增一個新的餐廳營運系統：Dirty Dishes / 洗滌系統。

這不是單純背景動畫。

它應該是一個很輕量、看得懂，而且真的會影響餐廳營運的 service-side bottleneck。

同時調整目前所有既有員工薪資。

⸻

Part 1｜Dirty Dishes System

一、核心循環

客人用餐完畢後：

客人吃完
→ 員工收桌
→ 把髒盤／髒杯實際拿回廚房
→ 放進 Dirty Dish Area
→ Dirty Dish Area 累積餐具
→ 玩家可以點這個區域安排洗滌
→ 員工走過去洗
→ 髒餐具數量逐漸下降
→ 洗完後該批餐具從 dirty system 消失

核心體驗：

出去的是一道道完成料理；回來的是一疊疊髒盤子。

我要看得到餐廳真的在運作。

⸻

二、Dirty Dish Area 初始容量 = 10

新增一個：

Dirty Dish Capacity

初始：

0 / 10

每次員工從桌上收回餐具，都會增加 dirty dish count。

盤、碗、杯目前可以共用同一個 capacity，不需要拆成三種 inventory。

例如：

髒餐具 7 / 10

到了：

10 / 10

就是滿了。

⸻

三、滿了之後的真正後果

Dirty Dish Area = 10/10 時：

不能再完成新的收桌工作。

不要讓髒盤憑空消失。

因此新的 dirty table 必須暫時等待：

* 員工可以知道它需要清理
* 但因為廚房沒有地方放新的髒餐具，所以不能完成收桌
* 桌子因此暫時不能正常 turnover

直到有人洗掉一些：

10/10 → 9/10 → 8/10

空間重新出現後，外場才能繼續把新的髒餐具收進來。

這就是這套系統的 gameplay consequence。

但注意：

Dirty Dish Capacity 不等於 clean plate inventory。

即使現在有：

10 / 10 dirty dishes

也不要因此讓 Cooking PLATING 出現：

* 沒盤子
* 沒碗
* 沒杯子
* 不能出餐

目前不要追蹤 clean plate / bowl / cup inventory。

Dirty Dish system 只控制：

收桌 → 髒餐具回收 → 洗滌 → turnover

不要擴張成餐具庫存模擬器。

⸻

四、要新增實際的洗滌空間，但不要新增房間

請先 audit 現有 Kitchen layout。

我不希望為了這個功能：

* 重畫廚房
* 新增洗碗房
* 改變現在漂亮的 kitchen composition
* 移動主要 Cooking stations

優先利用目前已存在的：

sink / sink-adjacent counter

把它做成一個自然的：

Dirty Dish + Washing Area

它不是 HOT / PREP / OVEN / PLATING 的第五種 chef station。

它是：

service-side operating station。

在現有 sink 附近找合理的位置加入：

* dirty dish landing area / rack
* sink washing position
* 必要的 dish stack visual

不要放巨大的「洗碗區」招牌。

讓它自然長在原本廚房裡。

⸻

五、髒餐具必須真的看得到

不要只有 UI：

7 / 10

廚房場景本身也要看得到。

例如：

0/10：
幾乎沒有髒盤。

1–3/10：
零星幾個盤／杯。

4–6/10：
開始形成一疊。

7–9/10：
明顯很多。

10/10：
看起來真的滿了。

不需要每一個餐具都精準畫成獨立 sprite。

可以使用幾個 visual tiers / stack composition。

但玩家不看數字，也應該大概知道：

「喔，髒盤快滿了。」

⸻

六、餐具要有物理移動

客人吃完後，不要：

桌子髒
→ 點一下
→ 桌子乾淨
→ 髒盤消失。

正確是：

員工到桌邊
→ 收盤／杯
→ 手上出現一疊 dirty dishes
→ 抱著走回廚房
→ 走到 Dirty Dish Area
→ 放下
→ dirty count 增加。

這個角色可以是 cleaner，也可以是 waiter。

如果 Dirty Dish Area 已滿：

員工不要把盤子 teleport 進去。

該桌保持等待清理狀態，等容量出現。

⸻

七、玩家點 Dirty Dish Area = 安排洗滌

這個 interaction 要像 Cooking station 一樣自然。

玩家看到髒盤區：

髒餐具 8/10

直接點場景中的髒盤／sink area。

不要跳複雜 menu。

點下去後：

系統安排一名目前可處理洗滌工作的合格員工。

Ticket / small feedback 可以顯示：

洗滌 · 秀琴阿姨前往中

角色真的走過去。

開始後：

洗滌 · 秀琴阿姨

⸻

八、洗滌動畫

員工到 sink：

→ 從 dirty stack 拿一個／一小批
→ 放到 sink
→ 洗／刷／沖
→ 放到 clean side / drying rack
→ dirty count 減少

例如：

8/10
→ 洗
→ 7/10
→ 洗
→ 6/10

不要：

點一下 → 8 個瞬間全部消失。

我要看到這是一項持續工作的 job。

可以有：

* 水流
* scrub
* rinse
* stack movement
* clean dish placement

但不用做 QTE。

⸻

九、洗滌可以中斷

如果員工正在：

8/10 → 7/10 → 6/10

不要求他一定要洗到 0 才能離開。

如果有更高優先工作、玩家重新安排，或 AI priority 合理要求：

可以在完成目前這一個 washing beat 後離開。

剩下：

6/10

就留在 Dirty Dish Area。

之後其他人可以繼續洗。

不要重置。

⸻

十、誰可以洗

第一版：

Cleaner

可以：

* 收桌
* 搬 dirty dishes
* 洗滌

而且相對積極處理 Dirty Dish Area。

Waiter

也可以：

* 收桌
* 搬 dirty dishes
* 洗滌

但正常 priority 應該仍然是：

* serve
* guest-facing work
* clear tables

Dirty Dish Area 接近滿時，washing priority 才提高。

不要讓 waiter 在有大量菜等著送時，所有人一起跑去洗碗。

Jill / generic chef

目前不要讓 AI 自動安排他們洗碗。

料理人力不應該因為髒杯子 4/10 就離開 HOT/PREP。

未來如果有特殊情況再討論。

Jill’s Kitchen｜Restaurant Workflow B：Pass、服務生多份配送、收桌、Dirty Dishes、洗滌與自動化完整重構

我現在要在 feature/cooking-gameplay 上繼續擴充新的 Restaurant Workflow。

這不是把 Jill’s Kitchen 改成高壓的 time-management game，也不是做 Diner Dash / Overcooked。

產品方向是：

餐廳裡的工作要真的有人做、真的有物理流動、真的可能形成 bottleneck；但員工會自己運作，玩家只在想介入時介入。

核心體驗：

前期：玩家學會做事。
中期：玩家和員工一起做事。
後期：員工自己能做事，玩家管理 bottleneck。

不要增加玩家手速要求。

不要讓玩家必須一直點。

不要加入 Game Over 型失敗。

不要讓玩家離開廚房看貓、熟客、故事或 Lounge 就受到不合理懲罰。

⸻

0. 先 audit，不要重複造輪子

開始前先完整 audit：

feature/cooking-gameplay

尤其確認現在已經存在的：

* Cooking work node
* HOT / PREP / OVEN / DRINK / PIZZA workflow
* batching
* chef proficiency
* staff claim / handoff
* station capacity
* waiter pickup
* cleaner / waiter 現有 AI
* Pass / heat lamps
* table dirty / clear logic
* crew duty / standby
* staff upgrade
* current salary data

不要平行做第二套系統。

新功能要接到現在已有架構上。

⸻

1. HARD PRODUCT RULE

整間餐廳現在應該形成四條可見工作流：

Cooking Flow

Order → PREP / HOT / OVEN / DRINK → PLATING → Pass

Service Flow

Pass → waiter pickup → table

Table Flow

guest finishes → dirty table → waiter / cleaner clears

Dish Return Flow

dirty dishes → Dirty Dish Area → washing

玩家玩的不是：

「一直快速點東西。」

玩家玩的是：

「現在到底是哪一條工作流塞住了？」

⸻

2. PLATING 與 Pass 必須徹底分開

延續最新 Cooking choreography canon。

PLATING 不是 Pass。

正確物理流程：

上一站完成
→ 食物留在原位置
→ handler 取得空盤
→ handler 去完成料理旁
→ 真正裝盤
→ handler 把完成餐點拿到 Pass

所以：

PLATING = making the finished dish into a plateable/servable dish

PASS = completed food handoff / pickup buffer

食物不能自己 teleport。

⸻

3. Pass 正式變成 Finished Food Buffer

Pass 不再是 plating station。

它是：

已經完成的餐點等待外場 pickup 的地方。

要有真正容量。

先 audit 現有 Pass / heat lamp / plate position。

優先沿用現有視覺。

不要重新設計廚房。

Pass capacity 可以隨既有餐廳／廚房工程成長。

例如概念上：

early：較少
mid：增加
mature：再增加

但不要先武斷改成任意數字。

先依現在實際 Pass visual 與現有 upgrade 決定。

Pass 滿時：

不失敗。

只是新的 completed plate 暫時不能放上去，因此 upstream plating / finishing 會安全等待。

不燒焦。

不降 quality。

不紅色 FAIL。

不倒數。

⸻

4. Waiter 不能被設計成一次只能拿一盤

這是 HARD RULE。

一般服務生有兩隻手，而且熟練服務生現實上可以一次拿多盤，或使用 tray。

所以：

服務生必須有 Carry Capacity。

不要設計：

一個 waiter = 一次只能一盤

這會讓後期看起來很笨，而且造成大量無意義走路。

⸻

5. Waiter Carry Capacity

建立一個簡單的：

carryCapacity

概念。

初期 waiter 可以合理一次帶至少 2 個 service units。

因為最基本就是兩手。

後續能力成長可以增加：

例如概念上：

* beginner：2
* experienced：3
* senior：4
* very skilled：4–5

最終數字要 simulation / visual test 後決定，不要只因為這裡舉例就硬鎖。

但：

絕對不要初期 = 1。

⸻

6. Service Unit 保持簡單

不要建立複雜重量系統。

第一版：

* 主菜 = 1 unit
* 飲料 = 1 unit
* 小食 = 1 unit
* 一般甜點 = 1 unit

不要做：

* 牛排 1.3
* 湯 1.4
* 酒杯 0.7

這些目前都不需要。

目標是：

玩家看得懂：

這個服務生一次大概可以拿幾樣東西。

⸻

7. Waiter pickup 不應該一有一盤就無腦衝

熟練服務生應該可以做非常短的 batching / anticipation。

例如 Pass：

* 炒飯 → Table 2
* 紅茶 → Table 2
* 牛排 → Table 5

一個 capacity 3 的 waiter 不應該一定：

炒飯一完成
→ 馬上拿一盤跑出去
→ 回來
→ 再拿紅茶

他可以合理判斷：

如果同桌下一份餐點即將完成，而且 Pass 不塞：

稍等一下，一起拿。

但這個等待必須很短。

不要因為想湊滿 tray 而讓客人一直等。

核心判斷：

send now vs wait briefly to consolidate

⸻

8. Waiter routing

Waiter 拿多份後：

不需要每送一份就回廚房。

他應該可以：

Pass pickup ×3
→ Table 2
→ Table 5
→ hand empty
→ return

優先 route：

* 同桌料理一起
* 空間方向合理
* 不要來回折返

不要求做 TSP 最佳化。

不需要完美演算法。

只要：

明顯比「一盤一趟」聰明。

⸻

9. Waiter 升級要改變行為，不只是速度

服務生能力提升至少可以影響：

* carry capacity
* batching willingness
* routing quality
* Pass pickup priority
